# 它挡什么,不挡什么

**先把边界说清楚,因为"安全"这个词单独拿出来是没意义的。**

## 它挡的

| 威胁 | 为什么挡得住 |
|---|---|
| **agent 被注入之后** | 这是主要威胁。一个能任意执行代码的 agent,在最坏情况下也拿不到私钥字节 —— 它最多能让守护进程替它签它被允许签的东西 |
| **同一个 uid 下的另一个进程** | 口令从 `/dev/tty` 读,不走 argv、不走环境变量、不走 stdin、不走 socket;钥匙文件 `0600`,目录 `0700` |
| **磁盘被偷** | 信封一半的熵来自 `device.secret`,另一半来自口令。少了任何一半都打不开,而且两者失败时的报错**一模一样** |
| **审计日志被事后编辑** | 链抓改动,锚抓截断 |
| **整个目录被拷到另一台机器** | **只有绑了硬件根才挡得住。** 没绑的话,信封今天仍然是一个拷贝就走得掉的东西 |

## 它不挡的

| 情形 | 为什么不在防线内 |
|---|---|
| **同一个 uid 下的另一个 agent 冒充你** | uid 是这个授权模型的地基,而它的粒度就是 uid |
| **你亲手把 `export-seed` 敲了一遍** | 见下 |
| **归档文件本身的离线爆破** | 归档的全部保护就是导出时那个一次性口令 |
| **机器的主人就是你的对端** | 这一条和前三条不同类,见下 |

### 关于"另一个 agent 冒充你"

要再细一层,得靠**可执行文件身份**(第三层)。那条路在 macOS 上经 `SecCode` 拿 cdhash —— **它提高门槛,但不是一道墙。**

### 关于 `export-seed`

关键不是"agent 不知道导出密码",而是 **agent 够不到那条通道**。

一个被注入的 agent 会做的事,是编一个像样的提示框让人类自己把密码敲进去 —— 所以"他不知道密码"根本挡不住这个。

真正成立的性质是:**导出不是一条 API,是一个要人坐在终端前敲的流程。** 这是"断链",不是"保密"。

再加一层:`export-seed` 在默认构建里**没有这段代码**。不是被拒绝,是不存在。

## 最后一条要单独说两句

因为它最容易被读成"熵不够",而**它不是**。

信封那几路熵(口令 / `device.secret` / HS)是设给一个**不在场**的敌人的:他拿走了 `~/.anp-keyd/` 的一份拷贝,回去慢慢算。硬件根把这一路补得更硬 —— 拷走的信封在别的机器上解不开。

但那些全是**事后**:东西被带走之后,他能不能把它恢复出来。

"别人的机器"是**当面**:东西正在被用,而用它的那段代码跑在他的地盘上。

- 解锁时 seed 就躺在守护进程的**普通内存**里 —— 硬件只当包装密钥、不当签名密钥(两个平台的芯片都不支持 Ed25519),所以到了签名那一步它必须出来
- 口令也一样,是从**他那台** `/dev/tty` 上敲进去的
- 也不必读内存 —— **那个二进制也是他的**

::: danger 两件事不是程度差别,是种类差别
**密码学挡"事后",挡不了"当面"。**

所以这一条不是"再补一路熵"收得了的。唯一的补法是换掉"谁在跑那段代码" —— 让守护进程待在你能控制的机器上、从远处请它签。
:::

那条路(让守护进程联网)在设计里是**被明确划掉的** —— 划掉的理由在[设计说明](/design/)里。
