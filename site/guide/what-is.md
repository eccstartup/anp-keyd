# 它是什么

**一个跑在你自己机器上的守护进程,替 agent 保管私钥,并按 RFC 9421 签 HTTP 消息签名。**

agent 手里从来没有私钥字节。它通过 Unix socket 说话,请求里可以带方法、URL、头、请求体 —— 唯独没有一个字段能装私钥。守护进程自己重建签名基、自己决定覆盖面,签完把签名头递回来。

## 它解决的那个问题

你想让一个 agent 替你去访问别人的服务。那个服务要认你是谁,所以它要一个签名。而签名要私钥。

直接把私钥给 agent 是最省事的做法,也是唯一一种做错了就收不回来的做法:agent 一旦被提示注入拿走控制权,它拿到的不是"能不能签"这个能力,而是**你在这台机器上的整个身份**,而且是永久的、可以带走的。

这个工具换了一条路:给 agent 一条**请求签名**的通道,而不是那把钥匙。

| | 直接把私钥给 agent | 用 anp-keyd |
|---|---|---|
| agent 手里有什么 | 私钥字节 | 一条 socket 通道 |
| 被注入之后 | 身份被完整拿走 | 只能让它签它被允许签的东西 |
| 覆盖面谁定 | agent 自己 | 守护进程 |
| 换机器 | 密钥文件跟着走 | 信封拷过去也打不开 |

## 两个门面,两种信任关系

命令分成两组,分界线是**谁在敲**:

- **走 socket 的**(`sign` / `list` / `status` / `document` / `unlock` / `lock`)—— 给 agent 用。连上守护进程要它做事,从始至终不碰私钥字节。
- **不走 socket 的**(`spec` / `keygen` / `publish` / `migrate` / `deactivate` / …)—— 给人用,在终端上当场打开信封。它们留在你自己的进程里,agent 够不着。

另外还有一条 MCP 门面,把其中几个转手给 MCP 客户端(`mcp` 子命令,单独的特性构建)。

::: warning 有一条纪律值得先说
凡是需要口令的命令,都要求一个**真的控制终端**。cron、CI、systemd 的 `ExecStartPre`、被 agent 拉起来的子进程都在这一条外面 —— 这是设计,不是遗漏。
:::

## 它明确不做什么

- **不托管任何东西。** `publish` 把 did.json 写出来,但**谁来把那个文件放到域名上是你的事** —— 那是别人验签时会去请求的地址。
- **不联网。** 守护进程不替你去取别人的 DID 文档。答得出来的是本机发布过的那几个。
- **不替你挑坐标。** DID 是"坐标 + 公钥"算出来的,而坐标必须是你写在规格文件里的那几个。由工具替你挑一个,等于替你决定身份挂在哪儿。
- **不做多用户细粒度授权。** 授权模型的地基是 uid,粒度就是 uid。

## 什么时候会想要它

- 你要让 agent 去调别人的付费 API,而对方按签名认你的身份
- 你不想把身份材料放进 agent 的进程空间 —— 那里会跑它自己写的代码、它装的依赖、它读到的网页
- 你手上有不止一个 agent,但不希望每个都各持一份可复制的凭据
- 你需要一份"谁在什么时候让哪把钥匙签了什么"的日志,而且这份日志被改过你希望能发现

## 什么时候它不合适

- **机器的主人就是你的对端。** 这条和前几条不是程度差别,是种类差别:密码学挡"事后",挡不了"当面"。解锁时 seed 就躺在守护进程的普通内存里,而那个二进制也是他的。详见[它挡什么,不挡什么](/concepts/trust-model)。
- **你要的是细到进程的隔离。** uid 就是这条线的粒度。
- **你想让它当密钥服务器。** 它不联网,那条路在设计里是被明确划掉的。
