# anp-keyd 设计说明

这份文档回答的是**为什么这么做**。要装、要用,看 [README](../README.md);
要看某个函数怎么写,读源码 —— 每个模块头上都有一段比这里更细的注释。

这里记的是那些**从代码里读不出来**的东西:威胁模型、被故意排除的做法、
一旦发布就不能再改的格式。改动它们之前请先读完对应那一节。

---

## 一、它挡什么,不挡什么

先把边界说清楚,因为"安全"这个词单独拿出来是没意义的。

**它挡的:**

- **agent 被注入之后**。这是主要威胁。一个能任意执行代码的 agent,在最坏的
  情况下也拿不到私钥字节 —— 它最多能让守护进程替它签它被允许签的东西。
- **同一个 uid 下的另一个进程**。口令从 `/dev/tty` 读,不走 argv、不走环境
  变量、不走 stdin、不走 socket;钥匙文件是 `0600`,目录是 `0700`。
- **磁盘被偷**。信封(WrappedKey)一半的熵来自 `device.secret`,另一半来自
  口令。少了任何一半都打不开,而且两者失败时的报错**一模一样**。
- **审计日志被事后编辑**。链抓改动,锚抓截断。

**它不挡的:**

- **同一个 uid 下的另一个 agent 冒充你**。uid 是这个授权模型的地基,而它的
  粒度就是 uid。要再细一层,得靠可执行文件身份(第三层),那条路在 macOS
  上经 `SecCode` 拿 cdhash —— 它提高门槛,但不是一道墙。
- **你亲手把 `export-seed` 敲了一遍**。见第六节。
- **归档文件本身的离线爆破**。归档的全部保护就是导出时那个一次性口令。
- **机器的主人就是你的对端**(在不由你控制的机器上使用)。这一条和前三条不同类:
  它不是"防护弱一点",而是模型的预设不成立 —— 前三条的预设是 uid,而 uid 的前提
  是**这台机器是你的**。

**最后一条要单独说两句,因为它最容易被读成"熵不够",而它不是。**

信封那几路熵(口令 / `device.secret` / HS)是设给一个**不在场**的敌人的:他拿走了
`~/.anp-keyd/` 的一份拷贝,回去慢慢算;硬件根把这一路补得更硬 —— 拷走的信封在别的
机器上解不开(§九)。但那些全是**事后**:东西被带走之后,他能不能把它恢复出来。

"别人的机器"是**当面**:东西正在被用,而用它的那段代码跑在他的地盘上。解锁时 seed
就躺在守护进程的普通内存里 —— §9.2 写明硬件只当包装密钥、不当签名密钥,两个平台的
芯片都不支持 Ed25519,所以到了签名那一步它必须出来;口令也一样,是从**他那台**
`/dev/tty` 上敲进去的。这一侧加多少路熵都不动他:他一路都不用碰,在解锁那一步等着
就行。也不必读内存 —— 那个二进制也是他的。

两件事不是程度差别,是种类差别:**密码学挡"事后",挡不了"当面"。** 所以这一条不是
"再补一路熵"收得了的,唯一的补法是换掉"谁在跑那段代码"—— 让守护进程待在你能控制的
机器上、从远处请它签。那条路(让守护进程联网)在 [ADAPTER.md](ADAPTER.md) §十 里是
被明确划掉的。

## 二、信封 vs 归档:两个不能混的东西

这一对区分是理解整个设计的钥匙,值得单开一节。

| | 信封 `keys/<thumbprint>.json` | 归档 `<thumbprint>.anpkeyd.json` |
|---|---|---|
| 熵从哪来 | 口令 **+** `device.secret`(+ 绑了硬件的话,第三路) | **只有**导出时的那个一次性口令 |
| 能搬机器吗 | **不能** | 能,这是它唯一的用途 |
| 口令可以复用吗 | 可以,是日常口令 | **不行**,一次性,强制独立 |
| 谁生成 | `keygen` / `import-*` | `export-seed`(默认构建里不存在) |

**信封搬不走,这是设计,不是缺陷。** 一半的熵是这台机器的 `device.secret`,
所以把 `keys/` 整个拷到另一台机器上,那边的 `device.secret` 不一样,信封就
打不开。反过来说:任何一个能在别的机器上打开的备份,都不可能由 `device.secret`
保护 —— 它只能靠人给的那个口令。这就是归档。

**绑了硬件根就是把这一条推到极致。** `device.secret` 和信封住在同一个目录里,
所以"拷走目录"这动作会把两者一起带走 —— 它挡的是"备份被拷走、目录没被拷走"
这种情形,而挡不住整个目录搬走。硬件根补的正是那一路:第三份熵**根本不在
文件系统上**,只在芯片里(见 §九)。代价是"导出必须在这台机器上做"。

**归档文件本身就是一份可以被离线暴力破解的口令保护文件。** 它的强度等于那个
口令的强度乘以 Argon2id 的成本参数,再没有别的了。所以:

- 导出时强制要一个不弱的口令;
- 导出**不重试** —— 一遍就够,不留循环;
- 口令必须和日常口令**不同**,而且守护进程在导出前强制先 LOCK。

## 三、两份冻结的格式

以下两份格式**一旦发布就不能改**。改了的后果不是报错,是**旧的备份打不开** ——
放在用户手里的那张纸、那个文件,是他仅有的一份。

### 3.1 助记词推导方案(`bip39-entropy-v1`)

```
24 个词  <──BIP-39──>  32 字节熵  ==  Ed25519 的 seed
```

**走的是熵的编码/解码,不是 BIP-39 的种子派生。**

标准 BIP-39 的用法是:

```
熵 → 词 → PBKDF2-HMAC-SHA512(词, 可选口令) → 64 字节种子
                ^^^^^^^^^^^^^^^^^^^^^^^^^^^ 这一层我们没有
```

**这里没有那一层。** 24 个词直接编码那把 32 字节的 Ed25519 seed。没有
PBKDF2,也没有 BIP-39 的可选 passphrase —— 那是第二个会丢的秘密,所以连
"默认关闭"都不给,直接不做。

**这两种读法会推出两把完全不同的钥匙,而且不会有任何报错。** 拿一个标准的
BIP-39 工具(`to_seed()`、`to_master_key()`、或者带 passphrase 的命令行工具)
去处理同一张词,得到的不是错误,是**另一个 DID**:纸上的词还在,打不开的东西
却不报错。换实现、换语言、换工具时,必须按这一份来。

为什么是 24 个词:32 字节 = 256 位熵 + 8 位校验和 = 264 位 = 24 × 11。收到的
词数不是 24,不是"能不能凑合",是"这根本不是我写出去的词",直接拒。

`derivation` 字段里写的就是这个版本号 `bip39-entropy-v1`;将来若要引入别的
方案,它带着自己的版本号并列存在,而不是把这一份改掉。

### 3.2 归档格式(`anp-keyd-archive` v1)

```text
┌─ 明文 ─────────────────────────────────────────────┐
│ format / version        这个文件是什么、哪一版       │
│ derivation              推导方案版本号(见 3.1)      │
│ did / kid / thumbprint  这把钥匙是谁的               │
│ created_at / wns_handle 什么时候造的、挂在哪个名字下 │
│ document                整份 DID 文档(**含 proof**) │
├─ 密文 ─────────────────────────────────────────────┤
│ kdf / aead / seed_ciphertext   32 字节 seed,就这样  │
└────────────────────────────────────────────────────┘
```

常量:`format = "anp-keyd-archive"`,`version = 1`,`derivation =
"bip39-entropy-v1"`,`kdf = "argon2id"`,`aead = "xchacha20poly1305"`。

明文那一半是**故意**明文的:那些信息本来就挂在域名上给所有人看,加密它只是
让人以为"这里也有秘密"。而且它有个实际好处 —— 一张打不开的备份,至少还能告诉
人"这是谁的备份"。

**AAD 里为什么塞文档摘要:** `did`/`kid`/`thumbprint` 绑住了"这是谁的钥匙",
但文档是整个搬过来的 —— 有人换掉文档里的公钥、再把 seed 挪过去,单看头是看不
出来的。所以 AAD 覆盖的是**JCS 规范化后**整份文档的 SHA-256。文档里任何一个
字节变了(包括与钥匙无关的字段)摘要就对不上,而且这一条**先于解密**发生。

## 四、磁盘布局

根目录默认 `~/.anp-keyd`(`--root` 可覆盖;`--system` 下是
`/var/lib/anp-keyd/users/<uid>`)。

```
~/.anp-keyd/
├── device.secret              0600  这台机器的第二个因子。丢了 = 信封全废
├── keys/<thumbprint>.json     0600  信封,一把一个
├── dids/<did>.json            0644  已发布的文档(含自签 proof),给外面看
├── audit/YYYY-MM.jsonl        0600  审计日志。按月分片,链 + 锚
├── log/serve.log              0600  守护进程的运行日志,给人排查用
└── run/
    ├── keyd.sock                    守护进程的 Unix socket
    └── keyd.pid               0600  它的 pid(`stop` 读这个)
```

`log/` 和 `audit/` 是**两样东西**,别混:审计是哈希链加锚,是对外的证据;
serve 日志是运行记录,随时可以删。把它们塞进一个文件,前者就失去了意义。

目录 `0700`,秘密文件 `0600`,公开文件 `0644`。写入一律先写临时文件再
`rename`(`write_atomic`),这样断电不会留下半个文件。

文件名里的 `<did>` 是**拍平过**的:DID 里的 `:` 换成 `_`,其余不在白名单的字符
同样换成 `_`(`did_safe`)。所以
`did:wba:example.com:agents:bot:e1_abc…` 落在
`dids/did_wba_example.com_agents_bot_e1_abc….json`。信封那边的 `<thumbprint>` 走
`is_safe_thumbprint` 单独把关 —— 两个都是外部输入,都必须挡住路径穿越。

`device.secret` 值得单说一句:**文件整个不见了**和**它是新生成的**,是两件事,
而且分开报。`device::load` 在文件缺失时报 `BadDeviceSecret`;而
`load_or_create` 生成一个新的 —— 新生成的那把打不开旧信封(报 `BadPassphrase`,
和口令错一模一样)。系统不会"顺手帮你恢复"。放在一起人才能看出自己丢了什么。

## 五、审计日志

`audit/YYYY-MM.jsonl` 按月分片。每一行是一条事件,和前一行**链**起来(少了
一行、改了一行,链就对不上);每个分片另外有一个**锚**,抓住整个文件被截断
这种情况 —— 链管不了"尾巴没了"。

链是**跨月延续**的:换月不重置,所以本月文件第一行的 `prev` 指的是上个月最后
一行。于是"总共有多少条"用的是记录自己带的 `seq`(累计),不是这个文件里数
出来的行数;`seq` 每一行必须正好比前一行大 1,不是就是被删过或改过号。

**打开日志要走的是一整条链,不是最后一个文件。** 链跨月延续,那么"本月对不对"
就取决于前面每一份月份文件 —— 只验本月那份,一个**已经过去的**月份连它的末行
一起被改掉就没人看得见(而这个月的记录会照样接着那条被改过的尾巴)。所以
`AuditLog::open` 从**最早**那份月份文件走起,那份的第一行必须接在 `GENESIS` 上:
它不是的话,要么更早的月份被删了,要么整条链是重写出来的。**代价是常数级的
读盘,而它躲不掉** —— 要发现旧月份被改过,就得把旧月份读一遍。这不是可以靠
往锚里多存一个摘要省掉的东西:链就在文件里,存一份整链摘要只是把同一件事说两
遍(`.anchor` 仍然只管它本来管的那件事:末条记录数和尾巴的哈希,也就是"被截断"
和"被回滚到旧版本")。

**写它的是多个进程,所以一次追加是一段临界区。** 守护进程攥着一份到进程
结束,而每一条 CLI 命令各自开一份 —— 它们完全跑得起来的时间正是守护进程正忙
的时候。两个写者各记各的 `records`/`tail` 去写,后写那行的 `prev` 就指向一条
不是它前驱的记录,链断。而链断是这个文件**唯一**用来指认事故的信号:让一次
合法的并发造出这个信号,比日志乱一点糟得多 —— 真的出了事和"有两个进程在写"
会变成同一句话,而人看见几次之后只会学会忽略它。

所以"读尾哈希 → 写记录 → 写锚"整段走一把 `<audit_dir>/.lock` 上的 `flock`
(和文档 CAS 那一段同一个办法,见 `src/did/migrate.rs`)。锁是那个 `.lock` 而
不是某一份 `.jsonl`:后者换月会换成另一个文件,锁它挡不住换月那一瞬间。锁
**只包住一次追加**,不包住 `AuditLog` 的一生 —— 攥着不放等于"守护进程在跑的
时候所有命令卡死",而那正是一次正常的并发操作。

锁里第一件事是**跟磁盘对账**:文件的字节数和自己记得的不一样,就说明别人写
过,把状态重读一遍;文件**变短**则拒绝写着走 —— 那是锚存在的意义,悄悄接着
写就把一次截断掩盖成了"看起来一直是这样"。

日志里**没有秘密**:没有口令、没有种子、没有私钥字节。它记的是"谁在什么时候
让哪把钥匙签了什么",以及 `IMPORT` / `EXPORT` 这类会改变状态的事。

**"会改变状态的事"包括本机自己那些。** 一条身份在这台机器上出现有两条路:
`IMPORT`(别人那份搬进来)和 `KEYGEN`(这里自己生一把)—— 只记前者,事后拿
一个 DID 问"它什么时候出现的"就漏掉最常走的那条。同理,`PUBLISHED` 记的是
文档落进本机 `dids/` 那一份,而 `publish --out DIR` **不记**:那条路本机一个
字节都没变,记下来会让人以为本地那份文档是它。`PUBLISHED` 和 `DOCUMENT_READ`
用的是同一个摘要函数,所以拿一个摘要在整份日志里搜一遍,得到的就是这份文档的
一生:谁什么时候写下去的、谁什么时候取走的、什么时候被改的。

## 六、导出为什么是缺席的,不是被拒绝的

```bash
cargo build --release                          # 默认:没有导出
cargo build --release --features seed-export   # 有导出
```

```toml
[features]
default = []
seed-export = []
mcp = ["dep:rmcp"]
```

默认构建里 `export-seed` **不存在**。不是"被拒绝",是**没有这段代码** ——
没有分支、没有环境变量、没有可翻的开关。一个能一键把整把身份抽干的接口,是
agent 被注入之后最想找的那个东西,所以它干脆不在二进制里。

导入则相反,**默认构建里就有**。理由不对称而清楚:恢复自己的身份不该需要一次
特殊编译;而交出身份应该。

导出这条路本身还有几条约束,都写在代码里:

- **断链,而不是保密。** 关键不是"agent 不知道导出密码",而是**agent 够不到那
  条通道**。一个被注入的 agent 会做的事,是编一个像样的提示框让人类自己把密码
  敲进去 —— 所以"他不知道密码"根本挡不住这个。真正成立的性质是:**导出不是
  socket 上的一个消息类型**(`wire::Request` 里没有导出变体),它只在这个进程
  自己的 `/dev/tty` 上、由人类本人操作。于是就算人类被骗着把密码敲进了 agent
  的聊天窗,agent 也**送不到守护进程**。
- **只接受本进程自己 `open("/dev/tty")` 拿到的终端。** 绝不接受一个经
  `SCM_RIGHTS` 传进来的 fd —— 那样 agent 可以自己开一个 pty,把从设备 fd 递
  过来,让守护进程以为自己在跟一个终端说话,于是渲染一个假提示、读走人类敲进去
  的东西。这一条在这里是**结构上成立**的:导出不是 socket 操作,这条路径从头到
  尾没有接收过任何 fd,所以守住它的方式是**不加那条代码**,而不是加一个检查。
- **没有 `--password`。** 口令只从终端读、关回显、读完 zeroize、不进日志。
  argv 会被 `ps` 看到,环境变量会被同 uid 的进程在 `/proc/<pid>/environ` 里读到。
- **独立口令、一次性、强制先 LOCK。** 导出密码必须**不是**日常解锁口令,否则
  "人类解锁了日常签名"就等于"人类授权了导出",能力没有分离。它只能用一次,
  不落盘、不复用。导出前先 `LOCK` 把正在进行的签名会话全部杀掉 —— 让导出变成
  一件有破坏性、看得见的动作,这是特性不是缺点。
- **没有控制终端 = 失败,没有降级路径。** cron、CI、被 agent 拉起来的子进程、
  systemd 的 `ExecStartPre` 都在这一条外面。

### 导入之后必须说两句话

`import-mnemonic` / `import-archive` 做完之后会打印两条提醒,它们不是客气话:

1. **克隆警告。** 导入出来的这把钥匙,和原来那台机器上的是**同一把**,不是
   副本意义上的"同一把"。两边都能签,而且验证方分不出来。
2. **托管提示。** 新信封用**本机新的** `device.secret` 和**本机新的**口令重新
   封装,seed 用完全程立刻清零,并记一条 `IMPORT` 审计。

## 七、命令行:两组命令,两种信任关系

**走 socket 的**:`sign` / `list` / `status` / `unlock` / `lock`。这些是**给
agent 用的** —— 它们连上守护进程,拿签名,从始至终不碰私钥字节。

**不走 socket 的**:`serve` 之外的其余命令。`keygen` / `publish` / `verify-doc`
是身份的生命周期操作,由人发起、在终端上做、当场打开信封。它们留在人类自己的
进程里,agent 够不着。

**为什么不把生命周期操作也做成 socket 消息:** `publish` 要签的正是**一份
文档**,如果把它做成消息类型,调用方就能让守护进程签任意一份文档 —— 那等于把
防盲签那套设计从后门拆掉。这个取舍和"导出不做成消息类型"是同一条道理。

### 谁决定文档的内容:规格进,文档出

上面那条边界落下来,就是一条很窄的接口:**外部给的是"这份文档该有什么"
(规格),不是"这就是那份文档"。** 文档由 keyd 自己构造、自己签。

这条线画在哪儿是有代价的,值得写清楚:

- **规格里只能有坐标和声明**,不能有公钥、不能有 proof,也不能有
  `verificationMethod`。公钥是 `keygen` 那一刻才存在的,proof 是签名的产物
  —— 任何一样能塞进规格,盲签那条后门就开了一半。
- **也不是所有"文档里的东西"都该开放。** 根密钥的 fragment(`key-1`)就没有
  进规格文件:它不是一条声明,是本工具自己认根密钥用的名字,生命周期代码按
  它来找"哪把是根"。开放出去等于允许造出一份本工具自己看不懂的文档 ——
  下一次重签会把根密钥当成附加密钥再挂一遍,而且不报错。
- **规格是唯一的来源**,`keygen` 和 `publish` 都读它,不各猜各的。从前
  `keygen` 会构造一份完整文档、只为了拿到里面的 DID 字符串然后把文档丢掉,
  而 `publish` 反过来从 DID 字符串重建文档 —— 中间任何"别处加上去的声明"
  都在这条来回里静默消失。
- **重发不许丢声明。** `publish` 不给 `--spec` 时,overlay 来自**本地那份正在
  被替换的文档**。重发一次文档顺手把 `service` 清空,是一个不报错的丢东西;
  而 `service` 里挂的正是 WNS handle 这类东西 —— 丢了它,等于换了一把钥匙
  之后这个名字不再属于你。
- **坐标对不上就拒。** `--spec` 的坐标必须和 `--did` 说的是同一处,对不上
  直接拒而不是挑一个信。

代价是流水线上多了一个文件。值得:那个文件正是"我想要什么"可以被人读到、
被 code review 到的地方,而它不含任何秘密。

### socket 协议

```
frame := u32_be(len) || payload
```

消息类型只有六种:`LIST_KEYS` `SIGN` `UNLOCK` `LOCK` `STATUS` `GET_DOCUMENT`,
回答是 `OK` 或 `ERR`。

对端身份拿不到就**拒绝**:没有"取不到就放行"的分支。这一层是整个授权模型的
地基,uid 是它给的;一旦有降级路径,降级的那条就是"任何人都能连上来签"。

对端身份分三层:

1. **内核给的 uid/gid** —— 地基。
2. **内核给的 pid** —— 用来在日志里指认是谁。
3. **可执行文件身份**(`cdhash:` / `sha256:`)—— 可选,`serve --allow-binary`
   才启用。多用户部署里这一条不能省,理由见第一节"不挡的"第一条。

### `stop` 为什么不是一种 socket 消息类型

守护进程要活得比那个终端久,所以 `serve` 默认把自己放进后台(**重新执行
自己**并加 `--foreground`,不是 fork)—— 服务管理器拉起来的那条路和它于是
是同一条代码路径。那就要有办法把它停下来。

**不走 socket。** 线上那几种消息类型是给 agent 那侧的契约;为了让人
能停一个守护进程去改它,是拿那侧的稳定性换一点便利。而且换不到什么:pid
文件这条路只需要一个数字,再加一句核对。

那句核对是这条路上唯一有分量的东西。**pid 会被内核回收** —— 守护进程死掉
之后,同一个号码可能落到任何一个新进程头上,而 `stop` 发的是 SIGTERM,对方
多半直接死。所以动手之前先问一句:占用这个 pid 的进程,跑的是不是**这个
二进制**?比的是 `(dev, ino)`,不是路径字符串 —— `~/bin/anp-keyd` 那种转发、
符号链接、以及"二进制被重新编译过"都会让路径字面不同,而 inode 不会。对不
上就什么都不做:不杀,也**不删 pid 文件**(看不懂的时候动手是最坏的选择)。

顺带一条不那么显然的次序:**pid 文件由绑定成功之后才写**。写在绑定之前的话,
一个注定要失败的第二个 `serve`(socket 已经被占了)会先覆盖**正在跑的那个**
的 pid 文件,再在退出时把它删掉 —— 症状是下一次 `stop` 对着一个活着的守护
进程说 "nothing is running"。

同一类陷阱在后台化的就绪判定里也出现过一次。父进程本来靠"连一下 socket"确认
孩子起来了,可是**别处已经有一个守护进程在那儿听着**时,这个条件一开始就
成立:父进程会连上别人,把"它早就在那儿了"报成"我们起来了",退出码 0,而
真正的原因(孩子在日志里说的 already served)被吞掉。所以判定加了一问:
能连上的那个 socket,**inode 得和起孩子之前那个不一样**。

后来那条连接本身也被去掉了。开了第三层(§七的 `--allow-binary`)之后,它会被
**拒** —— 探测就是一条连上就走的空连接,内核给的凭证读不出来,于是每一次
`serve` 都给自己记一条 `DENIED` 审计事件,外加一条 WARN。审计是防篡改的
证据,不该混进工具自己的噪声。判据换成"**那个 socket 文件的 inode 变了,
而且孩子还活着**":`bind()` 之后孩子那边每一步失败都以退出收场,绑上了就是
已经在 `listen` 了 —— 不需要真的去连一下。

这条判据后来又补了一问,因为上面那句"`bind()` 之后每一步失败都以退出收场"
少了半步:**步与步之间那段不是零。** `bind()` 和写 pid 文件之间有一小段,
在这段里 socket 已经是新的、孩子也活着,父进程于是把终端还回去,而紧接着
敲 `stop` 的一方读到的是一个还不存在的 pid 文件。症状是"守护进程明明起来
了,`stop` 却说没在跑",而且只在负载上来时才现 —— 实测撞到过。所以现在就绪
= **inode 变了 + 孩子活着 + pid 文件里记的就是这个孩子**。这一问不改次序
(仍然是先绑定、后落 pid 文件),只是把"还没写完"和"已经写完"分开。

---

### 覆盖面对调用方只开放"加",不开放"减"

`sign --cover NAME` 可以要求**多**覆盖一些分量,但**不能少**。签名基由守护
进程自己重建,覆盖面也是 —— 调用方说要加什么可以,说要减什么不行。一条"能减
覆盖面"的路等于给了调用方一个"悄悄签得比你以为的少"的开关。

## 八、测试分层

六类测试,失败的含义不一样:

| 文件 | 回答的问题 | 红了意味着 |
|---|---|---|
| `src/**` 的单元测试 | 这个函数在它的假设下对不对 | 代码写错了 |
| `tests/cli.rs` | 真起一个 `anp-keyd` 进程、真的在一个终端上敲命令,走不走得通 | 给人看的那一层坏了 |
| `tests/signature_end_to_end.rs` | 整条路走通没有 | 接口对不上了 |
| `tests/negative.rs` | **产品承诺的那十件事今天还成立吗** | **有人把一道墙拆了** |
| `tests/tpm.rs` | **真芯片上:封得住、开得回、根没了就拒绝** | 第三路熵那一层坏了 |
| `tests/vectors/` + `tests/vectors.rs` | 外部标准还认不认我们的实现 | 见下 |

`tests/cli.rs` 那一层必须存在,而且必须用**真终端**,理由见那个文件头上那段:
`ops::Session::open` 自己调 `tty::open()`,没有注入口 —— 一个能被调用方塞进
"另一个终端"的实现,正是第六节里那条 `SCM_RIGHTS` 攻击要利用的东西。所以
唯一的测法是和人类一样用它:开一对 pty,让子进程 `setsid` + `TIOCSCTTY`。

另外四个文件各管一个单一命题:`tests/probe.rs`(体检说的都是真的)、
`tests/mcp.rs`(MCP 那五个工具就是全部,一个 raw 都没有)、
`tests/hardware.rs`(硬件绑定那条路的形状:版本分派、AAD、硬件不在、口令错、
拒绝降级)、`tests/no_key_material_on_disk.rs`(走完一遍之后,磁盘上扫不出
密钥材料)。

`tests/negative.rs` 用**公开 API**,不碰 crate 内部:一份"从外面看这个系统"的
检查,如果必须借道内部状态才跑得起来,那它检查的就不是这个系统了。

### 关于 `tests/vectors/`

`tests/vectors/` 里的 JSON 是**权威文本的抄本**,取自 RFC 8032 §7.1/§7.3、
RFC 7638 §3.1 与 RFC 8037 附录 A.3、RFC 9421 附录 B.1.4/B.2.6、RFC 8785
§3.2.2/§3.2.3 与附录 B。每一个文件都带 `_source`,写明它抄自哪一节。

**如果向量测试红了,先怀疑实现。** 改一个向量让测试变绿,等于把这个文件存在
的理由删掉。抄不出逐字节一致结果的用例,我们**不收** —— 宁可少一个用例,也不
放一个"差不多"的期望值进去。

其中一条最接近生产路径:RFC 8032 TEST 1 的公钥,经过我们自己的 `e1_` 段计算,
必须等于 RFC 8037 A.3 公布的那个指纹
`kPrK_qmxVWaYVA9wwBF6Iuo3vVzz7TxHCTwXBygrS4k`。两个 RFC,一份实现。

另外那一对向量是**反例**,而且它俩挨着放才看得出意思:RFC 8032 §7.1 的
`TEST SHA(abc)` 和 §7.3 的 `TEST abc` **是同一把钥匙**(公钥都是
`ec172b93…`)。前者把 `SHA-512("abc")` 那 64 字节**当作消息本身**直接签;后者
是 Ed25519ph —— 对 `"abc"` 做预哈希再签。我们会算前者(它就是普通 Ed25519,
哈希只是消息内容),**绝不算后者**:ph 出来的签名必须和我们的不一样。我们不做
预哈希。

## 九、硬件根(M5)

### 9.1 问题的形状

信封里那两个秘密都是软件的:口令(在人脑子里)+ `device.secret`(磁盘上 32
字节)。**把 `~/.anp-keyd/` 整个拷到另一台机器、又知道口令,今天就能拿到
私钥;一份离线备份也一样,只是慢一点。**

要补的是一路**不可导出**的熵:它在芯片里,拷不走。

### 9.2 为什么是"HS 进 HKDF",不是"硬件包 KEK"

把 KEK 直接交给硬件包起来听着更省事,但那要求 KEK **落盘** —— 它今天是派生
出来的、从不落盘,包它就得先把它存下来。多一步,而且更弱。

```
HS  = 32 随机字节,由硬件封装后存进信封(hs_ciphertext)
KEK = HKDF-SHA256( argon2id(口令) ‖ device.secret ‖ HS, salt )
DEK = open(KEK, dek_ciphertext)
seed = open(DEK, sk_ciphertext)
```

从这个角度看,这一整块**只是给 KEK 多添了一路熵**:信封的两层结构、`exact32`、
"同一个 nonce 两个 key"这些一个字节都没动,少任何一路都开不了。

**硬件只当包装密钥,不当签名密钥。** 两个平台的硬件都不支持 Ed25519,所以
让芯片里的 P-256 去封一把对称秘密,Ed25519 那把 seed 仍然躺在被包装的密文里。

### 9.3 记录格式 v2

- **version 1 一个字节都不改**,旧信封照旧能开。
- 硬件绑定的写 **version 2**:`hardware` 和 `hs_ciphertext` 进 AAD 头
  (`AadHeader`,见 `src/keystore/record.rs`)。所以"绑了哪种硬件、哪个 tag"
  本身是**被认证过**的 —— 把 `hardware` 从 SE 改成 TPM、或者把 tag 换一个,
  都会在解 KEK 之前先 `AadMismatch`。
- `unwrap` 按 version 分派;`validate()` 收 1 和 2。
- **归档(`anp-keyd-archive`)格式一个字节都不改。** 它冻结,而且必须可搬 ——
  给它加上硬件绑定就等于把"备份"这件事删掉。

### 9.4 两个平台的封装原语不一样

| | macOS Secure Enclave | Linux TPM 2.0 |
|---|---|---|
| 原语 | ECDH(P-256) | `TPM2_Create` + `TPM2_Unseal` |
| 怎么封 | SE 公钥 + 一个临时密钥对 | 直接封给 TPM |
| 封的时候要硬件吗 | **不要** | 要(密封在 TPM 里做) |
| 开的时候 | 调 SE 做 ECDH | 调 TPM 做 Unseal |
| 定位符 | 钥匙串标签 | 持久化句柄 |
| PCR 绑定 | — | 可选,**默认不绑** |

那两行"要不要硬件"不对称是刻意的,而且有用:**封在任意机器上做、开只能在本
机做**。PCR 默认不绑,因为绑了的话内核或固件一升级就把用户锁在门外 —— 那是
一种自己给自己造的、到那天才知道的丢失。

### 9.5 四条不变量

1. **助记词和归档这两侧永远不碰硬件。** `mnemonic::to_words` 的签名不变。
   否则芯片坏了 = 钥匙没了 = 等于没备份。导出/导入是唯一允许的搬家路径,
   而那条路径的产物是一把**硬件无关**的钥匙。
2. **没有可用硬件根就拒绝生成,不做静默降级。** 不给"看起来在保护、其实
   没有"的中间态。
3. **硬件根是第三层,不替代 `device.secret`。** 后者管"备份拷走没用",前者
   管"拷到别的机器没用"。两件事,两道锁。
4. **导出现在必须在本机做**(它要先解信封)。这是有意的代价,纪律写在 README
   里:趁机器活着把那 24 个词抄下来。

### 9.6 macOS 那半边的发行前置

SE 私钥**唯一的持久化机制就是钥匙串**,写钥匙串要 `application-identifier`,
而这个 entitlement **只有 Apple 签发的证书能给**。(26.7.1 / arm64 实测:未
签名二进制建永久 SE key → `errSecMissingEntitlement`;ad-hoc 签名 + 手写
`keychain-access-groups` → 进程被内核 SIGKILL;同一台机器上 ad-hoc 签名**不带**
那个 entitlement → 正常运行,但 SE key 一退出就没了。)

**所以 SE 版本必须以签名身份分发,`cargo build` 的产物做不到。这是发行决策,
不是代码里能补的一环。** Linux/TPM 没有这道门槛,走 `/dev/tpmrm0`,而且
`swtpm` 能在本机模拟 —— 所以那条路径是可以真测的。
